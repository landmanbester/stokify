# stokify

The runnable demonstrator for hip-cargo's recipe → Ray transpiler. It is a
deliberately small three-step pipeline — **init → process → image** — on
synthetic data, built to the restricted-subset contract the transpiler
compiles (see `DEMONSTRATOR.md` for the monitoring demonstration and
`hip-cargo/docs/design/transpile-rfc.md` for the rationale).

## Installation

```bash
pip install -e ".[full]"    # or: uv sync --extra full
```

## Usage

```bash
stokify --help
uv run --extra full python demo.py                # hand-written runner
uv run --extra full python demo.py --transpiled   # generated runner
```

## Transpilation: how it works

This repo contains the transpiler's input, its committed output, and the
hand-written reference to diff against:

| Artifact | Role |
|----------|------|
| `src/stokify/recipes/stokify.yml` | **Input** — a restricted-subset stimela recipe (linear steps, `=recipe.x` bindings, `{recipe.x}` interpolations, nothing else) |
| `src/stokify/transpiled/` | **Output** — generated by `hip-cargo transpile`; committed, never hand-edited |
| `src/stokify/runtime/` | **Reference** — the hand-written exemplars the RFC's spike produced; diff these against `transpiled/` to see that the code generation is mechanical |

Regenerate (idempotent — unchanged files are not rewritten):

```bash
hip-cargo transpile --recipe src/stokify/recipes/stokify.yml \
                    --output-dir src/stokify/transpiled
```

The transpiler runs four stages (details:
`hip-cargo/docs/wiki/transpile.md`):

1. **Parse** the recipe with hip-cargo's shared recipe/cab front-end.
2. **Validate** it against the restricted subset, naming every violation
   (formula DSL, aliases, loops, non-python cabs, unknown refs, …).
3. **Infer** the *data* edges — init's `output` path string equals process's
   `input-data` string, so init → process is a real dependency, not just
   declaration order — and statically detect each cab's in-memory sibling:
   `stokify.core.init.init` has an `init_inmem` next to it, found by scanning
   the module source with LibCST (the module is never imported).
4. **Emit** `tasks.py` (one `@ray.remote` per step: timed lazy import,
   diagnostics annotation, `*_inmem` call), `runner.py` (ObjectRef chaining —
   the driver holds only opaque refs and never materialises a dataset),
   and `cli.py` (a Typer `run` generated from the recipe's `inputs:`).

### The in-memory contract

A cab command `pkg.mod.fn` opts into ObjectRef chaining by providing a
sibling in the same module:

```python
def fn_inmem(dataset, memory_mode, job_id, pipeline_run_id, work_dir, **cab_params): ...
#            ^ first positional only when the step consumes an upstream output
```

Path-typed parameters are dropped from the call (the dataset flows through
Ray's object store instead of disk); a cab without an `_inmem` sibling is
still transpiled, falling back to its declared disk-persisting command.

### Run the transpiled pipeline

```bash
stokify transpiled run --base-dir /tmp/stokify_out --memory-mode greedy --monitor
uv run --extra full python demo.py --transpiled     # self-verifying, prints RESULT: PASS
uv run --extra full python -m pytest tests/test_transpiled.py -m slow   # e2e on a local Ray cluster
```

The generated pipeline streams the same lifecycle events, metrics, and
per-task diagnostics through the monitoring stack as the hand-written one —
`demo.py --transpiled` gates its PASS on exactly that.
